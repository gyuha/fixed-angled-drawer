# 실행 기록 — 4개 변형(폭 × 두께)을 폴더별로 생성

## 조각별 결과
- S1 변형 테이블 + 전환 함수 + 4회 순회 생성, `IN_D` 정합 검증 추가 — ✅ 계획대로
- S2 기존 파일 이관(`output-8cm/` 폐지, 3mf 2개 이동) + `screenshot.py` 경로 변경·렌더 재생성 — ✅ 계획대로
- S3 README 4변형 구조 반영 — ⚠ 계획에 없던 판단 하나: 문서에서 검증 항목 **개수 표기를 제거**

## 계획대로 된 것
- 루트에서 한 번 실행하면 4폴더가 생성된다: `output/{w70,w80}-wall{2.4,3.0}/`, 각 폴더에 STL 8개 + FCStd 1개.
- **변형당 33항목 × 4변형 = 132개 전부 PASS, FAIL 0.** 신규 `variant params` 항목이 변형마다 `IN_D == D - WALL`을 확인한다.
- 변형별 세트 재료량이 서로 다르게 실측됐다 — 폴더만 생기고 내용이 같은 사고가 아님을 증명한다:
  | 폴더 | 세트 재료 |
  |------|-----------|
  | w70-wall2.4 | 510.9cm³ (634g) |
  | w80-wall2.4 | 548.3cm³ (680g) |
  | w70-wall3.0 | 600.8cm³ (745g) |
  | w80-wall3.0 | 646.2cm³ (801g) |
- 사용자 슬라이서 프로젝트 2개를 **삭제하지 않고** 대응 폴더로 이동: `output/w70-wall2.4/fixed-drawer.3mf`, `output/w80-wall3.0/fixed-drawer.3mf`. `output-8cm/`은 폐지.
- 렌더 5장은 `output/` 루트에 유지되어 README 이미지 링크가 그대로 살아 있다(확인). `screenshot.py`는 `REF_VARIANT = "w70-wall2.4"`의 FCStd를 읽는다.

## 현장 결정 (계획에 없던 판단)
- **문서에서 검증 항목 개수 표기를 제거했다.** 이번에 개수를 세려다 정규식 추정이 32/34로 흔들렸고, 이 프로젝트에서 이미 두 번(31↔32) 문서와 실제가 어긋났다. 스크립트가 항목별 PASS/FAIL과 종합 결과를 찍으므로 숫자를 문서에 중복 관리할 이유가 없다 — "그 출력이 유일한 기준"이라고 명시했다.
- `set_variant()`가 서랍 껍데기 캐시(`_SHELL`)와 `_DRAWER_INFO`를 비운다. 캐시가 변형 간에 남으면 이전 변형의 무게중심·개구 위치가 그대로 재사용되어 조용히 틀린 형상이 나온다.
- FCStd 문서명을 변형별로 다르게 하고(`pen_holder_<folder>`) 저장 후 `closeDocument`한다 — 한 프로세스에서 4개를 연속 만들면 같은 이름이 충돌한다.

## 막혔던 곳 / 학습
1. **봉인 스크립트가 브랜치 루트를 요구해 처음에 거부됐다**(exit 2, `EMPTY no-forge-state`). 현재 브랜치가 `feature/filament-saving`인데 forge 상태를 최상위 `.forge/`에 써 왔기 때문이다(ADR-0011은 비default 브랜치에서 `.forge/branch/<브랜치>/`를 요구). 이 브랜치에서 만든 작업(#3 활성 슬롯, #4 백로그)만 브랜치 루트로 옮겨 해결했고, main에서 봉인된 `done/`·`retro/`·`CONTEXT.md`·`adr/`는 그대로 두었다 — 그건 main의 이력이다.
2. 브랜치 전환을 **세션 중간에 인지하지 못하면 상태가 엉뚱한 곳에 쌓인다.** 작업 시작 시 브랜치를 확인하는 습관이 필요하다.
